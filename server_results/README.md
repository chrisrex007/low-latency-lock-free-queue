# Published Benchmark Results

These are the authoritative numbers for this project. They were **not** produced on a
development laptop — that environment is too noisy for figures worth publishing.

## Machine

Intel Xeon E5-2697 v2 @ 2.70 GHz — dual socket, 12 cores × 2 threads per socket,
**48 logical CPUs across 2 NUMA nodes**, 30 MB L3 per socket. Full details, including
the CPU/NUMA/SMT topology map and frequency governor state, are in `environment.txt`.

Note the NUMA layout is **interleaved**: node 0 owns the even-numbered CPUs, node 1 the
odd ones. Naive "first N CPUs" pinning would therefore split producers and consumers
across sockets — the benchmark reads the real topology from sysfs instead.

## Method

- Threads pinned to cores, memory bound to one NUMA node.
- Median of 5 timed iterations, plus one discarded warm-up (the machine's frequency
  governor was not under our control, so the first iteration of a configuration runs
  at a low P-state).
- Total operations held constant across every thread configuration, partitioned
  statically up front so the only contention measured is contention on the queue.
- Run-to-run standard deviation: **0.00–0.55 Mops/s**.

## Headline numbers (64B messages)

- **15.3x** MPMC lock-free over the mutex baseline at 1P1C (57.63 vs 3.76 Mops/s).
- **2.6–3.7x** sustained under contention, scaling to 24 threads.
- **5.74x** cross-socket penalty for the lock-free queue, against only **1.09x** for the
  mutex — the mutex is so dominated by kernel overhead that NUMA placement barely
  registers, which is exactly why removing that overhead makes placement matter.

## Reproducing

The CSVs here were generated by a NUMA-aware driver script and a topology-discovering
variant of `bench/benchmark.cpp`, both of which were specific to this server and are not
part of the repository. The committed `bench/benchmark.cpp` produces the same
measurements on a single node; on a multi-socket machine, wrap it in `numactl`:

```bash
numactl --cpunodebind=0 --membind=0 env BENCH_PIN=1 ./benchmark > same_node.csv
```

Because these CSVs came from that server-specific variant, their schema differs from
what the committed `bench/plot.py` expects — the charts here are the ones generated at
the time, not regenerated from the committed tooling.
